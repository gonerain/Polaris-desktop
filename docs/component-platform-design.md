# Polaris 架构说明

## 1. 系统全貌

Polaris 把安装和启停放在组件层，把跨组件协作放在能力层。一个组件可以提供多项操作和事件，每项可以有自己的依赖。

```text
桌面与插件管理    桌宠 · 画布 · 窗口承载 · 组件管理 · 插件源
对话与业务        Polaris Agent（随包）；微信 · 日程 · Agent Bridge（独立插件源）
                         │ 通过公开能力协作
基础组件          运行管理（生命周期）· 协作（目录与路由）· 授权（访问检查）
公共代码          启动装配 · 协议 · SDK · 进程通信
```

9 个随包组件的实现位于 [next/components](../next/components)，公共代码位于 [next/polaris_platform](../next/polaris_platform)。**组件管理**是用户选择安装、授权和提供方的桌面入口；**运行管理**维护安装记录和运行实例，无界面时也能工作。

## 2. 从插件源到运行实例

首次打开桌面时，组件管理读取默认源配置。以微信为例，插件源组件下载仓库快照、读取索引和清单，组件管理选中指定的组件 ID，再由运行管理启动它。用户卸载后，下次启动仍保留这个选择。[默认源配置](../next/components/manager/default-sources.json)

这里有三种身份：**组件 ID** 标识软件；**安装 ID** 标识本机这一次安装，授权和提供方选择据此保存；**实例 ID** 标识本次运行。重启组件会使旧句柄失效，卸载重装还会更换安装 ID，因此不能继承旧授权。

## 3. 能力注册、依赖与替换

便签的本地操作叫 `get`，通过 `provides` 注册公开契约 `notes.read@1`。标签的 `label` 操作用 `requires` 把这个契约命名为 `note`，处理时调用 `ctx.call_required('note', …)`。另一插件只要实现相同契约、种类和读写语义，就可以用不同的本地操作名提供便签读取。[便签实现](../next/examples/notes/main.py) · [标签实现](../next/examples/labeler/main.py)

只有一个可用提供方时，平台在首次使用时记住选择；有多个时，由用户为这项使用方能力选定。插件运行中可以注册或撤回能力。已选提供方撤回读取操作后，生成标签会报告缺少依赖，查看已有标签仍然可用。

## 4. 一次调用如何获得授权

`用户请求 → 标签.label → 便签.get`。协作组件把 `note` 解析到具体安装和操作；每一跳都检查该操作是否同时在**原请求的权限范围**和**当前有效授权**内。第二跳的直接调用者是标签，但沿用原请求的权限，所以用户可能有权生成标签，却在读取便签时被拒绝。

同进程调用使用 SDK 上下文，独立进程通过 stdio 传递 JSON 和临时请求令牌。事件回调取发布方与订阅方权限范围的交集。需要跨重启继续的任务保存用户委托的操作范围，恢复后每次调用仍检查撤权。[组件契约](../next/CONTRACT.md)

## 5. 点开桌宠时发生什么

桌宠为本次展开选定同一个画布实例，先订阅收起事件，再请求显示；画布确认已显示后，桌宠才隐藏。期间即使用户换了默认画布，本次状态查询仍发往原实例。收到匹配本次会话 ID 的收起事件后，桌宠恢复显示。

窗口承载拥有原生窗口；画布拥有卡片的位置、尺寸和折叠状态；挂载的插件创建自己的视图并管理业务数据。因此从画布移除一张卡片只释放这份展示，插件可以继续运行。

## 6. 状态与故障恢复

| 现象 | 状态归属与处理 |
|---|---|
| 首次下载失败 | 插件源管理快照，组件管理显示失败原因，可单独重试该源。 |
| 提供方离线 | 运行管理保留安装与选择；原安装恢复后可以重新绑定，平台不会重放业务请求。 |
| 能力可见却调用失败 | 授权组件保存具体安装的授权。检查请求来源和被拒绝的操作，尤其是嵌套调用的下一跳。 |
| stdio 写调用超时 | 写入结果未知。适配器拒绝该实例的后续业务调用，须核实结果并重启实例。 |
| 重启后恢复界面 | 桌宠保存位置，画布保存布局，各插件保存自己的业务数据。窗口句柄和事件订阅随实例重新建立。 |
