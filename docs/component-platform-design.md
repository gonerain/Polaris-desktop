# Polaris：由组件组成的软件平台

设计稿，尚未接入现有应用。本设计必须遵守 [README「组件设计原则」](../README.md#组件设计原则)；下面的组件划分与协议选择是实现方案，不能替代或缩减这些约束。它取代早期调用原型作为后续平台化工作的设计依据。

## 平台本身也是一组组件

Polaris 发行版提供一组默认组件和启动配置。开发者的软件可以加入这组组件，也可以替换其中遵守相同接口的实现。画布、桌宠、窗口承载、运行管理、协作和授权都属于组件，拥有自己的身份、接口、数据和生命周期。

组件可以提供界面、后台功能、其他组件使用的服务，或者同时提供这些能力。没有界面、没有导出操作的软件也可以运行；作者需要跨组件协作时，再公开相应能力。组件内部的语言、框架、存储和业务组织由作者决定。

统一组件身份和契约，不代表所有组件拥有相同权限，也不要求把每个类、函数和辅助库拆成组件。一个组件可以包含多个相关能力。组件边界首先服务于独立开发、运行和替换。

| 默认组件 | 自己负责的功能 | 替换边界 |
| --- | --- | --- |
| 运行管理 | 安装记录、启动与停止、实例身份、运行状态、更新；提供管理界面 | 保持公开运行管理接口；既有安装身份和记录通过公开导入、导出契约迁移，内部存储格式由实现决定 |
| 协作 | 能力目录、查找与绑定、调用路由、可选事件订阅 | 使用协作接口的组件不依赖其内部目录或连接实现 |
| 授权 | 保存授权决定、处理授权申请、核验和撤销访问范围 | 授权策略与界面可替换，调用方继续收到一致的允许或拒绝结果 |
| 窗口承载 | 拥有原生窗口、渲染资源和视图实例，提供展示句柄与状态 | 初版由 Qt 实现；只有依赖它的展示能力要求窗口存在 |
| 画布 | 通过展示句柄安排布局、占格、显示、隐藏与展开 | 维护自身布局，不拥有被展示组件的业务数据，也不决定它们的运行状态 |
| 桌宠 | 形象、动画、气泡及自身交互 | 关闭或卸载后，其余组件和管理入口仍可使用 |
| 日程、Agent、微信及第三方软件 | 各自的功能、规则、数据、视图与协作流程 | 经公开接口协作；保留各自的开发方式 |

这些职责不依赖默认组件的固定名字。启动配置把基础角色绑定到某个已安装组件；后续组件可以查询角色或明确选择目标组件。遇到多个符合接口的实现，使用用户配置的绑定，不随机选择，也不因为新组件出现就自动替换目标。

## 自举与运行

可执行入口只做自举：读取启动配置、构造选定的基础组件、连接其公开接口、启动运行管理组件。只有配置明确列为自举必需的基础能力启动失败时，才报告缺失并停止本次启动。默认配置不把窗口、画布或桌宠列为无界面运行的必需依赖。它不创建日程模型，不解释业务事件，也不拥有桌宠或画布状态。

基础组件先构造，再绑定，最后启动。例如协作组件得到授权组件的核验接口，运行管理组件得到协作组件的登记接口。启动时已经取得的基础接口无需再次发现；授权核验也不再发起一次“授权核验的授权核验”。这些绑定端口只交给配置指定的组件，其用途、调用方和范围由启动配置明确。它们属于基础机制的控制接口，不能作为普通业务请求绕过授权的通道；基础组件替别人处理业务请求时仍使用该请求的授权上下文。

初始管理权来自本机用户选定的启动配置。普通软件不能靠声明相同名称获得管理身份，也不能批准自己的权限申请。替换授权或运行管理实现属于用户管理操作；同一套组件标准允许不同的权限级别。

默认组件状态为 `installed → starting → running → stopping → stopped`，启动或运行异常进入 `failed`。管理界面分别展示运行状态和视图状态。隐藏视图不停止组件，停止组件也不自动删除数据。

第一阶段的运行约定：

- 所有组件，包括运行管理、协作、授权等基础组件，都适用能力登记、撤回、失效通知和重新绑定的契约。退出后撤销其公开能力和旧调用句柄；依赖它的能力按声明降级或报告不可用。
- 独立进程组件先收到停止请求，超时后由运行管理组件报告仍在停止，用户可选择强制结束。默认不反复自动重启。
- 同进程组件按契约合作停止。Python 导入、线程和 Qt 对象不能承诺任意安全卸载；无法释放时要求重启。
- 动态加入与退出不等于无缝热升级：新实例就绪后重新发布能力，调用方重新绑定；期间允许相关能力不可用。基础组件也不豁免这条要求。若某阶段只能通过重启更换实现，必须记为尚未完成动态生命周期的实现限制，不能据此宣称已经满足 README。

依赖区分整个组件启动必需、某项能力必需和可选协作，并标明对应接口及版本要求。缺少启动必需依赖时，报告组件不能启动；运行中某项能力的必需依赖退出或变得不兼容时，提供方将受影响能力标为不可用并说明缺少哪个接口，其他能力按声明继续运行。可选依赖缺失只减少相应功能。依赖恢复后，使用方按原有选择重新绑定并更新能力状态，不自动改用其他实现，也不重放失败的业务请求。

运行管理与协作组件提供依赖状态和变化通知；哪些能力受影响、如何降级，由使用方维护。首版使用显式依赖列表和版本要求，不引入自动下载依赖或复杂求解器。

## 开发者接入

一个安装包最少包含组件 ID、显示名、包版本、平台协议版本和运行入口。操作声明可以由 SDK 在启动后生成，无需在配置文件和代码里维护两份列表。

拟定的开发模式清单如下，SDK 和命令尚未实现：

```json
{
  "id": "org.example.notes",
  "name": "便签",
  "version": "0.1.0",
  "platformApi": 1,
  "entry": {
    "mode": "process",
    "command": ["python", "main.py"]
  }
}
```

开发模式从组件目录运行这个命令。发布包要声明所需运行环境或自带可执行程序；安装器不把第三方依赖直接安装进 Polaris 的 Python 环境。初版只承诺从本地目录加载，不先建设商店、签名分发和依赖下载系统。

提供两种接入路径，共用公开协作契约：

- **独立进程**是第三方软件的默认方式。作者可以使用任意语言，SDK 处理标准输入输出上的消息收发。现有软件也可以附加一个适配程序，调用自己的公开接口。
- **同进程**用于用户信任且符合当前 Python/Qt 版本要求的组件，例如直接提供 QML 视图的组件。省去进程通信，但接受对宿主稳定性和依赖版本的影响。

独立进程用于语言和依赖独立、故障分离，不等于操作系统沙箱。平台授权约束通过平台发起的协作；首版不声称限制第三方程序全部文件、网络或系统访问。

SDK 的目标使用方式：

```python
# 接口草案，用于说明开发体验。
component = Component()

@component.operation("get", access="read")
def get_note(id: str):
    return notes.get(id)

@component.operation("create", access="write")
def create_note(title: str):
    return notes.create(title)

component.run()
```

开发者可以使用函数注册或手动提供操作处理器，不强制继承平台基类。SDK 处理发现、上下文、错误封装和通信。停止钩子、事件、视图、参数 schema 都按需加入。SDK 提供受支持的执行与事件循环接入方式，作者遵守相应线程约定；不自动猜测任意框架的线程要求，耗时业务处理不能阻塞宿主 GUI 线程。

## 标准协作接口与数据自由度

共同约定只涵盖：谁提供能力、调用哪个操作、携带什么参数、怎样返回结果或错误，以及调用的身份和授权范围。

公开操作至少声明名称、读写级别和接口主版本。主版本默认 1；描述、参数和返回说明用于帮助开发者与工具理解接口。JSON Schema 可选，SDK 可以从简单类型标注生成基础说明；未提供 schema 的操作仍然能被程序调用，业务校验由提供方负责。

为了让不同语言的软件互通，首版**可移植协作接口**采用 JSON 可表示的数据。约束落在协作协议和传输适配器，而不是某个认识业务字段的公共校验器：适配器能够报告消息无法编码，却不判断“任务日期是否合法”。新增组件不需要修改适配器中的业务类型列表。README 允许必要的跨边界输入校验；共享机制校验自身协议、身份和消息格式并不违反能力归属，业务含义仍以提供组件为准。

同进程组件内部仍可以使用任意 Python/Qt 类型。原生界面接口也可以使用明确公布的 Qt 类型，但须声明只适用于对应视图适配器，不能把它当作所有软件均可调用的可移植接口。初版不要求每种内部对象都能自动跨进程传递，也不实现通用对象转换框架。

这是面向开放软件接入的取舍：常用协作拥有统一格式，内部实现和明确标注的原生扩展保持自由。早期原型接受任意 Python 对象的方式可保留为本地实验，不能据此声称组件已经具备跨语言兼容性。

协作组件提供以下最小能力：

- `discover / describe`：发现组件和已公开的操作、事件与视图声明。
- `advertise / withdraw`：组件在运行中发布、更新或撤回自身能力及可用状态。登记来源绑定到运行管理组件确认的实例身份，不能替其他组件声明能力。
- `bind / call`：绑定指定组件或用户选择的接口实现，调用已公开操作。
- `watch`：得知组件和能力加入、退出、变更；客户端可重新查询当前状态。
- `subscribe / publish`：可选的在线事件能力，订阅需要授权。初版不承诺离线消息、重放或跨组件全局顺序。

能力变更完成后，目录、有效调用句柄与授权选项都反映新的声明；即使订阅通知尚未送达，调用检查也不能继续使用已撤回的能力。通知携带声明修订标识，客户端发现跳变或重连时重新查询快照。业务请求不会因为能力恢复而被服务自行重发。

SDK 隐藏这些操作的通信细节。调用参数不能自行填写可信身份；运行管理组件根据进程连接或同进程实例生成身份，协作组件在转交时附上原始请求方、直接调用方、授权来源及有效范围。

组件能按目标 ID 调用特定软件。需要可替换实现时，依赖命名接口及其主版本，由用户选择实现；仅有相同操作名不足以宣称兼容。普通插件不必先定义一个全平台标准接口。

## 协作由发起组件完成

例如提醒组件订阅日程公开的到期事件，再调用桌宠的消息接口：

- 日程组件决定何时到期，维护自己的提醒规则。
- 提醒组件选择事件、发起和取消订阅，决定本次通知交给谁，处理订阅或调用失败并汇报结果。
- 桌宠组件决定消息如何展示。
- 协作组件按接口维护订阅与投递事件，返回状态和错误；授权组件检查访问范围。重新订阅、业务重试和结果汇报由提醒组件决定。

这段流程属于提醒组件，可以关闭或更换。平台不内置“日程到期一定让桌宠说话”的分支。

同一组件内部的一项完整功能可以用一个公开操作完成全部校验和执行。跨组件流程按普通程序编写，发起方处理超时、取消、部分成功和结果汇报。调用超时只表示没有及时得到结果；写入是否发生需要提供方的查询能力确认。平台不自动重放业务写入，也不提供默认的跨组件事务或流程引擎。

## 授权与兼容升级

按目标组件及具体操作、事件订阅项记录授权，由授权组件提供批量选择和“只读”等便捷交互。允许使用通用订阅接口，不代表允许订阅所有目标或未来新增事件。一次授权只覆盖当时列出的能力；插件无需自己实现一套权限窗口。授权组件消费目录变化，组件加入、退出及能力变化都会更新可选择的权限项。退出项可保留为供用户撤销的离线授权记录，但不能显示为当前可用能力。

两种标识分开保存：

- **稳定授权**绑定安装身份、具体能力项（操作或事件订阅）及其授权语义版本，用于保留用户决定。
- **运行期句柄**绑定具体实例，用于防止旧请求误调用到更新后的实例。

常规重启和兼容更新可以继续使用既有能力授权，但调用方须绑定到新实例。新增操作或事件订阅项默认未授权，包括运行中发布的新能力；读变写、扩大原有能力的权限含义或不兼容升级需要重新授权。新安装的软件冒用同一个组件名称，不视为原安装的更新。

默认由接口主版本和读写级别确定授权语义版本。作者仅在权限含义变化却需要维持接口主版本时，显式增加授权修订号。平台无法自动识别作者隐藏的语义变化；初版依赖作者履行契约与用户的安装信任，避免引入一个无法兑现的“自动证明兼容”系统。

调用链不自动借用被调用组件的长期权限。组件间继续传递当前授权上下文，只能收窄；缺少某项权限时返回可处理的申请信息，由授权组件面向用户处理。改成异步、放进队列或延迟执行，都不能改变原请求的授权来源和范围。

组件自主运行的定时任务可以使用用户另行明确授予它的后台权限。用户把一次请求转成长期任务时，需要新的明确授权记录，包含任务范围与来源；不能把请求换一个任务名或请求 ID 就转用组件已有的长期权限。

## 画布、窗口和桌宠

组件可声明零个或多个视图。提供方拥有视图定义和业务模型；窗口承载组件通过公开视图接口创建、销毁渲染实例，拥有原生窗口与渲染资源；画布持有并释放展示句柄，维护自己的布局。画布与窗口承载都不能因释放展示资源而销毁提供方的业务实例。

显示或隐藏只改变视图状态；停止组件是独立的生命周期操作。视图实例的重建、草稿保存和恢复由提供方的视图契约规定，不把未说明的共享对象或内部状态作为依赖。窗口承载不可用时，相关展示能力不可用，运行管理的非界面能力和其他不依赖视图的功能继续运行。

首版提供可信 QML 视图和外部窗口入口。普通桌面软件可以在画布上有一个卡片入口，点击后打开自己的窗口；不承诺把任意程序窗口嵌入画布。网页承载需要后续视图适配器，当前 PySide6-Essentials 配置不默认增加 WebEngine。

画布需要的尺寸、格子和标题属于画布接口，不能成为所有后台组件必须填写的字段。组件管理界面可以通过窗口承载组件单独打开，桌宠和画布都不充当唯一管理入口。

桌宠可以公开动画、气泡和显示能力，也可以拥有自己的设置页。它通过公开接口打开画布，不持有日程、Agent 或微信对象。更换桌宠形象或实现，不应修改运行管理、协作或业务组件。

## 缺失和故障

下表中的独立运行以组件正常停止或独立进程故障为前提。同进程组件若导致宿主进程崩溃，需要重启 Polaris，不能保证同进程的其他组件继续运行。

| 变化 | 行为 |
| --- | --- |
| 隐藏一个视图 | 只改变可见性，能力与业务实例保持运行 |
| 桌宠组件停止 | 自身能力停止；不依赖桌宠的管理入口和其他组件继续运行 |
| 画布组件停止 | 释放它持有的展示句柄；后台能力与独立窗口按各自依赖继续运行 |
| 窗口承载不可用 | 依赖它的视图不可用；运行管理的非界面能力和无界面组件继续运行 |
| 一个普通组件退出 | 对应句柄失效；调用方收到不可用错误，其他组件不被统一停止 |
| 可选依赖退出 | 使用者自行减少相关功能，协作服务报告能力变化 |
| 必需依赖退出 | 使用者将依赖它的能力标为不可用并报告原因；恢复后重新绑定，不重放旧请求 |
| 协作组件不可用 | 新发现和平台调用返回不可用；组件自身计算与独立界面仍可运行 |
| 授权组件不可用 | 受保护的平台调用与新授权返回不可用，不能自动当作已授权 |
| 运行管理组件不可用 | 生命周期操作暂停，其他能力按实际依赖继续；重新自举可用于恢复，不能把重启恢复等同于已实现运行中替换 |

第一阶段不缓存可绕过授权核验的长期调用通道，也不在故障时循环调用目录或授权服务。事件用于提示变化，重新查询是取得当前状态的方式。

## 下一版独立原型的验收

沿用“先独立原型、后决定迁移”的范围。先验证架构，不同时改现有日程、微信、Agent 或 UI。

1. 从一份装配配置启动运行管理、协作、授权和两个示例业务组件；基础组件也有相同的身份、描述与生命周期接口。
2. 一个示例运行在独立进程，另一个发起协作；把提供方切换成进程内实现，调用方业务代码不变。
3. 替换协作或授权组件的实现，示例插件无需改动；分别验证退出期间依赖能力不可用、新实例加入后重新绑定。只有重启替换通过时，应记录动态替换尚未实现。
4. 画布和桌宠作为独立可选组件登记。第一步用测试替身验证停用后的依赖行为；真实视图迁移再单独验证显示和关闭，不把替身测试宣称为 GUI 已支持热卸载。
5. 加入具有新业务字段的组件，仅修改插件自己的代码与声明；运行管理、协作、授权不增加分支。
6. 运行中发布、撤回操作和事件后，发现结果与权限选项同步更新；新增能力未授权，撤回能力不能继续调用或投递。兼容重启保留既有授权，旧实例句柄不能调用新实例。
7. 独立进程组件退出、崩溃、超时和可选依赖缺失都有可观察结果，无关组件能继续运行；同进程宿主崩溃按重启处理。
8. 给一个最小插件目录、一个可运行 SDK 示例和一条开发启动命令，验证作者无需接触平台内部模块。
9. 普通插件不能自行批准权限，嵌套调用、排队任务和基础控制接口均不能扩大业务请求授权；长期任务另行授权后仍能追溯来源与范围。
10. 窗口承载缺失、必需依赖退出与恢复、仅隐藏视图分别验证；不能用“组件最终还能重启”代替这些行为。

当前 `prototypes/component_layer` 只验证了部分调用边界，缺少以上装配、进程接入、基础组件可替换和兼容升级机制。后续原型按本设计重新组织，不以旧 Registry 的类划分限制平台结构。

## 与 README 原则的核对

下面是设计责任与验收的对应关系，不是实现已经通过验收的声明。

| README 原则 | 设计约束 | 验收证据 |
| --- | --- | --- |
| 能力归组件所有 | 业务规则和状态由提供方维护；迁移数据走公开契约，不要求保留内部存储格式；共享校验限于各自协议 | 更换存储或内部实现，使用方无需修改；同一业务规则只有所属组件解释 |
| 能力与展示分开 | 画布也是组件；窗口、展示句柄和业务实例各有负责人；隐藏只改变可见性 | 隐藏或停止画布、缺少窗口承载时，分别验证仍可用的能力与业务状态 |
| 协作有明确负责人 | 发起方组织流程、订阅、失败处理与结果汇报；共享服务维护机制并反馈错误 | 制造订阅失败、调用超时与部分成功，检查由发起方处理，没有底座业务分支 |
| 依赖与退出行为明确 | 区分启动必需、能力必需与可选依赖；所有组件适用加入退出契约；资源卸载限制单独记录 | 加入、退出、失联与恢复后，受影响能力状态明确，无关能力按声明继续；仅重启替换不算动态生命周期通过 |
| 能力自动发现，使用范围明确授权 | 运行中能力发布与撤回更新目录和权限项；新能力未授权；同步、异步和后台协作均保留明确来源与范围 | 验证目录与权限选项变化、新能力拒绝、撤回立即失效、调用链与异步任务不借权 |

README 的四个边界问题同时用作评审门槛：保持接口契约更换实现不应迫使使用方改动；退出后剩余能力必须可说明；新增组件不应要求旧组件增加业务分支；一项业务规则由所属组件统一解释。接口扩展或新协作场景确实需要调用方改动时，应把它列为显式功能变化，而非声称原契约已经覆盖。
