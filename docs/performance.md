# 资源测量与按需界面

## 测量口径

不能把安装包大小当内存，也不能把工作集与私有提交混为一谈。
不同渲染后端、窗口状态、运行时长、任务量和字体缓存的读数不能直接相减归因。
所有受控诊断使用内存或临时任务库、临时内联脚本；不增加持久测试套件。
正式运行仍使用 Qt 默认图形后端，不为了较低数字强制软件渲染。

Windows Python 3.13 / PySide6 6.8.3 的受控源代码诊断：
每个阶段单独进程，`QT_QPA_PLATFORM=offscreen`、`QT_QUICK_BACKEND=software`，
3秒预热后运行6秒，测量 `GetProcessMemoryInfo.PrivateUsage`，空任务库。

| 场景 | 私有提交 MB |
|---|---:|
| QApplication + 空 Qt Quick 窗口 | 36.1 |
| 静态桌宠 | 37.4 |
| 动画桌宠 | 41.5 |
| 优化前：启动即创建全部页面 | 59.2 |
| 优化后：首次展开才创建工作台 | 52.6 |
| 继续推迟菜单/退出对话框对象创建 | 51.1 |

最后一项相对原受控样本少8.1 MB，约14%；这是单轮样本，不是长期统计或峰值上限。
动画已通过 currentFrame 变化确认播放；短样本 CPU 计数为0，受计数精度影响，不能声称动画零成本。

此前正式 Windows 程序默认后端的10秒样本为：工作集194.4 MB、私有提交153.5 MB，
12逻辑核下整机平均 CPU 0.646%（单核口径7.75%）。
这与离屏软件诊断不是同一渲染环境，差额不能直接认定为某个模块的开销；
还需要检查默认图形后端、驱动、实际界面状态等因素。

同一旧版进程长时间待机后，8秒样本的私有提交148.6 MB，整机 CPU 0.032%（单核0.39%）。
这说明启动样本也不能代表稳定待机。总工作集此时约819 MB，而
`QueryWorkingSet` 按 `PSAPI_WORKING_SET_BLOCK.Shared` 位统计的非共享驻留仅22.6 MB，
其余约796 MB为可共享驻留页。**可共享不等于已经被其他进程共享，更不等于免费**；
不能把整个工作集算作独占物理内存，也不能只报非共享驻留而忽略私有提交。
该进程加载了 D3D11 和 NVIDIA 用户态驱动；模块映像大小不等于实际驻留分摊，尚未做分项归因。

新包的实际桌面样本（Qt默认后端）记录到：私有提交172.5→171.6 MB，
非共享驻留92.3→87.4 MB，整机 CPU 0.065%→0.033%（初始10秒、较长待机8秒）。
检查时已有菜单弹层窗口及 Controls 模块，因此不是“从未打开任何控件”的受控冷启动状态；
旧进程运行时长和页面缓存状态也不同。**当前没有证据证明实际桌面私有提交降低14%**，
更不能把工作集从约819到342 MB解释为优化幅度。14%只指上述同条件离屏源代码样本。
随后顺序冷启动旧包和新包，各在桥就绪后预热3秒、采样8秒：
旧包私有提交149.3 MB，新包152.9 MB；整机 CPU 分别0.293%和1.042%。
两个进程都加载了 Controls 动态库；没有锁定鼠标触发的动作和驱动缓存状态，短样本 CPU 不作因果判断。
这次对照仍未观察到默认桌面私有提交的下降，不应宣称实机内存优化成功。

本轮可以确认的是推迟了界面对象创建，并保持功能；不保证 Controls DLL 完全不加载。
实际默认后端的主要分配仍需进一步分析，不能将差额全部归咎于图形驱动。

## 本轮实现

- 唯一 `CalendarTaskStore` 属于主窗口，生命周期不再依附日程画布。
  后台提醒、存储恢复、组件 API 在任何页面创建前就可用。
- `Workspace.qml` 在第一次展开时按 URL 加载；日程、Agent 页面分别在首次访问时创建。
- 菜单和保存失败对话框单独按需加载，纯桌宠启动不创建 Controls 弹层对象。
- 已打开的页面**保留实例**，不在收起或切页时销毁，以保留输入草稿、视图状态和共享模型。
  因此打开工作台后内存可能上升，收起不承诺回到最初数字。
- 动画素材、帧率、画质、完成事件语义和生产渲染后端不变。

## 验证边界

需检查：冷启动无页面、未开页面时 API 写入及结束气泡、先 Agent 后日程、
共享模型唯一性、完整态往返、收起再展开实例不变、首次右键、首次保存失败退出保护。
原生 Windows 程序的运行计数只用于观察资源，不调用真实日程业务操作。
